# tar-vernのブラウザ対応計画

## 1. 目的と決定事項

tar-vernのtar生成・展開をブラウザとNode.jsの両方で利用できるようにする。tar/ustarの処理を共通化し、Node.jsのファイル操作を別の公開エントリーへ分離する。

通常のファイル選択では`File.size`をファイルの長さとして渡し、`File.stream()`から本文を逐次読み取る。サイズを調べるために本文全体を先読みしない。この方針は利用者との議論で決定した。

本書は調査結果と実装計画を保存したものである。計画に沿った実装と段階ごとの検証を完了した。実施結果は10章に記録する。本変更は破壊的変更を含む2.0.0としてリリースする予定とし、公開APIの旧形式との後方互換性は担保しない。Node.jsでtarの生成・展開とファイル操作ができることは維持する。利用者向け文書では、変更したAPIや動作の説明箇所に短い移行注記を添える。

本書では次の用語を使う。

| 用語 | 意味 |
| --- | --- |
| エントリー | tarに格納するファイルまたはディレクトリー1件 |
| チャンク | ストリームで受け渡すバイト列の一部分 |
| 逐次処理 | 内容をチャンク単位で読み書きし、本文全体の保持を前提にしない処理 |
| バックプレッシャー | 出力を読む側の進行に合わせて、入力の読み取りと内部の蓄積を抑える動作 |
| 共通処理 | Node.js固有のモジュールや型に依存しないtar処理 |
| Web Streams | ブラウザとNode.jsで利用できる標準のストリームAPI |
| 接続処理 | 共通処理とWeb StreamsまたはNode.jsのストリームをつなぐ処理 |
| ESM/CJS | JavaScriptのモジュール形式。ESMは`import`、CJSは`require`による利用に対応する |

## 2. 調査時点の実装と調査結果

調査対象はコミット`7ac8b1f`のコードである。Node.jsへの依存はファイル操作だけでなく、tarの処理と公開型にも含まれている。

| 対象 | 現在の状態 | 変更方針 |
| --- | --- | --- |
| [packer.ts](../../../src/packer.ts) | `Buffer`でヘッダーと本文を扱い、Node.jsの`Readable`を返す。gzipには`zlib`を使う | バイト処理を共通化し、Web Streamsから利用できるようにする |
| [extractor.ts](../../../src/extractor.ts) | 入力とファイル内容のストリームが`Readable`で、解析にも`Buffer`を使う | 環境に依存しない解析処理とストリーム接続へ分ける |
| [utils.ts](../../../src/utils.ts) | メモリ上のデータを扱うヘルパーと、`fs`・`path`を使うヘルパーが同居する | 共通ヘルパーとNode.js専用ヘルパーを分ける |
| [types.ts](../../../src/types.ts) | 公開型に`Buffer`と`Readable`が含まれる | 共通の公開型からNode.jsへの参照を除く |
| [index.ts](../../../src/index.ts) | ファイル操作を含むAPIを単一のエントリーから公開する | 共通APIとNode.js専用APIの公開エントリーを分ける |
| [vite.config.ts](../../../vite.config.ts) | Node.jsモジュールを外部依存として残す | 共通成果物からNode.jsへの依存を除き、複数エントリーを生成する |
| [vitest.config.ts](../../../vitest.config.ts)と[tests](../../../tests) | Node.js上のテストで、ファイル操作と外部のtarコマンドを使う | 共通処理のテスト、Node.js連携テスト、実ブラウザ検証を用意する |

調査時のブラウザ向けViteビルドは、`fs/promises`の`stat`を解決できず失敗した。通常のライブラリビルドでは、生成したESMにも`stream`・`zlib`・`fs`などのimportが残っていた。ViteはNode.jsのモジュールを自動でブラウザ用に補わないため、外部依存の設定変更だけでは対応できない。[Viteの説明](https://vite.dev/guide/troubleshooting.html#module-externalized-for-browser-compatibility)

Node.js v24.15.0で通常のビルドと既存57テストの成功を確認した。ただし、ローカルの`node_modules/.bin/vite`が空ファイルだったため、`npm test`では起動できず、ViteとVitestの実体CLIを直接実行した。また、インストール済みの`screw-up`は0.12.0で、package.jsonの指定する0.13.0以上と一致していなかった。実装開始時にnpmによる通常の実行経路を復旧し、基準となる結果を取り直す。実ブラウザでの実行は未確認である。

## 3. 対応範囲

対応対象は通常ファイルとディレクトリーを含む現在のtar/ustar処理、非圧縮tar、gzip圧縮したtar、メタデータの受け渡し、キャンセルとエラー処理である。

ブラウザでは文字列、`Uint8Array`、非同期反復可能なバイト列、Web Streams、`File`、`Blob`を扱う。Node.jsでは共通APIに加えて、実ファイルの読み書きとディレクトリー走査を提供する。

対象ブラウザは必要なWeb標準APIを備えるChromium、Firefox、WebKitを基本とする。Node.jsの最低対応バージョンは22.17.0とし、22.17.0と24.15.0で検証した。ブラウザはPlaywright MCP 0.0.83に対応するChromium 155.0.8059.12、Firefox 156.0、WebKit 26.6で検証した。ブラウザの取得バージョンはpackage-lock.jsonで固定する。未対応環境向けの互換ライブラリを暗黙に追加しない。

次の機能は今回の実装範囲に含めない。

- サイズ不明入力を一時ストレージへ保存して読み直す機能。
- サイズ計測のために入力を二度読みする機能。
- 出力ファイルへ書き戻し、tarヘッダーを後から確定する機能。
- ブラウザでの任意のローカルパスへのアクセスや、OSの所有者・アクセス権の再現。
- ブラウザのディレクトリー選択や保存先選択に固有のファイルシステム連携。
- 新しいtar形式や、リンク・特殊ファイルなどへの対応拡張。
- 旧APIの別名や返却型を維持するためだけの互換実装。

## 4. サイズと逐次処理

### 4.1. サイズが必要になる単位

tarはファイルのサイズを含むヘッダーを書き、その後に本文とブロック境界をそろえるパディングを書く。サイズが事前に必要なのは、格納する個々のファイルである。アーカイブ全体のサイズとエントリー数は事前に確定する必要がない。[GNU tarの形式説明](https://www.gnu.org/software/tar/manual/html_node/Standard.html)

展開時も入力tar全体のサイズは不要である。各ファイルのサイズは入力ヘッダーから取得するため、内容をストリームとして消費すれば逐次展開できる。

### 4.2. ファイル選択からの入力

選択した`File`のサイズを`length`へ渡し、本文を`stream()`から供給する。`Blob`も同じ扱いにする。`File`は`Blob`の機能を持ち、どちらもサイズとストリームを取得できる。[File API仕様](https://w3c.github.io/FileAPI/#blob-section)

この経路では`arrayBuffer()`による全体読み取りや、ヘルパー内部での全チャンク収集を行わない。ヘルパーを呼んだ時点で本文を最後まで読まず、tar出力の消費に合わせて読み取る。

長さの単位は本文のバイト数とする。`length: 0`はサイズが既知の空ファイルとして扱い、未指定とは区別する。現在の`if (!length)`による判定は変更する。

長さは非負の安全な整数で、対応するtar形式に格納できる範囲とする。負数、小数、`NaN`、`Infinity`、表現範囲を超える値は、そのエントリーの出力開始前に拒否する。

宣言した長さと実際の入力バイト数が異なる場合は、生成を失敗させる。超過分を次のエントリーとして出力したり、不足分を黙って補ったりしない。すでに出力したデータは取り消せないため、受け手はストリームが正常終了した場合だけ生成成功と判断する。

### 4.3. 長さを省略した汎用入力

ストリームまたはジェネレーターの長さを省略した場合は、現行の「本文全体をメモリへ収集し、長さを確定してからエントリーを作る」動作を共通処理でも提供する。この経路が省メモリの逐次処理ではないことをAPIと利用者向け文書に明記する。通常のファイル選択ではこの経路を使わない。

サイズ不明でもメモリ使用量を抑える方法は議論したが、今回は実装しない。

| 方法 | 成立する条件と制約 |
| --- | --- |
| 一時保存して計測する | 入力を一度読みながら保存し、確定後に再読出しする。ファイル全体を保存する容量と後始末が必要で、そのエントリーのtar出力開始は入力完了後になる |
| 入力を二度読む | 同じバイト列を再取得できる必要がある。一度しか読めない入力や、読み直すと内容が変わる入力には使えない |
| 仮ヘッダーを後から更新する | 書き戻せる非圧縮の出力先が必要で、サイズとヘッダーのチェックサムを更新する。現在のストリーム出力やgzip出力にはそのまま適用できない |

これらはtarのヘッダー先行という制約から考えられる実装方法である。標準tarの単一エントリーを、サイズ不明のまま、一度の読み取りで後戻りできない出力へ確定出力する機能とは区別する。

## 5. APIとモジュールの構成

### 5.1. 共通API

パッケージの`tar-vern`から、tarの作成・展開、エントリー型、メモリ上のデータからのエントリー作成を公開する。実行時のimportと型定義の両方から、Node.js固有の依存を除く。

バイト列は`Uint8Array`、内部のチャンク供給は`AsyncIterable<Uint8Array>`を基本とする。既存の非同期ジェネレーターによる処理を利用し、Web Streamsとの接続を加える。

計画上の公開APIは次の形を基本とする。新しい補助関数名の細部は各段階の実装時に既存APIとの対応を確認して確定する。

| API・型 | 変更後の役割 |
| --- | --- |
| `createTarPacker` | エントリー列を受け取り、`ReadableStream<Uint8Array>`を返す |
| `createTarExtractor` | `ReadableStream<Uint8Array>`または`AsyncIterable<Uint8Array>`を受け取り、エントリーを非同期列挙する |
| `FileItem.content` | 文字列、`Uint8Array`、長さ付きのストリームまたは非同期反復入力を扱う |
| `getContent('string')` | そのファイル全体を文字列として取得する |
| `getContent('bytes')` | そのファイル全体を`Uint8Array`として取得する |
| `getContent('readable')` | そのファイルの内容をWeb Streamsとして取得する |
| `createFileItem` | 文字列またはバイト列からファイルエントリーを作る |
| `createReadableFileItem`・`createGeneratorFileItem` | 長さが既知なら本文を事前収集せず、入力をエントリーへ接続する |
| `createDirectoryItem` | 指定されたメタデータまたは既定値からディレクトリーエントリーを作る |
| `createBlobFileItem` | 追加する補助関数の仮称。`Blob`または`File`から、サイズが既知のファイルエントリーを作る |

`createBlobFileItem`ではアーカイブ内のパスを明示的に受け取る。`File`の更新日時はメタデータの初期値に利用できるようにし、利用者の明示指定を優先する。`Blob`にはファイル名やOSの所有者情報がないため、ファイル名からの推測やOS属性の取得は行わない。

### 5.2. Node.js専用API

`tar-vern/node`から、`createReadFileItem`、`storeReaderToFile`、`createEntryItemGenerator`、`extractTo`などを公開する。現在の`createDirectoryItem`に含まれる実ディレクトリーの`stat()`処理も、Node.js側へ分離する。

Node.js専用ヘルパーは共通のエントリー型を使い、ストリームの変換は接続部分に限定する。`Readable.toWeb()`と`Readable.fromWeb()`の公式ドキュメントとAPIコメントを確認し、対応対象で安定APIとして利用できることを確かめる。[Node.js Web Streams](https://nodejs.org/api/webstreams.html#nodejs-streams-interoperability)

`extractTo`も、ファイル全体を`getContent('buffer')`で取得する現在の処理から、内容のストリームを保存先へ流す処理に変更する。展開対象のメタデータや、既存のファイル操作で実現している動作はテストで確認する。

### 5.3. バイト列と文字列

`Buffer.alloc`、`Buffer.concat`、`copy`、`write`、`toString`などを、バイト配列の確保・コピーと`TextEncoder`・`TextDecoder`へ置き換える。512バイトのヘッダー、パディング、終端ブロック、チェックサム計算は共通処理に残す。

UTF-8のバイト数と文字数を区別し、日本語や絵文字を含む名前をバイト境界で破損させない。本文先頭にある文字コードの識別用の記号BOMは、内容として保持する方針とする。`TextDecoder`の既定動作との差をテストする。数値フィールドはtarのASCII表現として扱う。[Encoding仕様](https://encoding.spec.whatwg.org/#interface-textdecoder)

### 5.4. gzip

共通のgzip処理には`CompressionStream('gzip')`と`DecompressionStream('gzip')`を使う方針とする。tarの生成・解析と圧縮処理を分け、非圧縮の処理はgzip APIがない環境でも利用できるようにする。gzipを指定して必要なAPIが使えない場合は、非圧縮へ切り替えず明示的に失敗させる。

現在の`zlib.createGzip({ level: 9 })`とは異なり、Web標準APIには圧縮レベルの指定がない。圧縮済みバイト列の一致やレベル9を要件にせず、展開した内容とメタデータで正しさを確認する。[Compression仕様](https://compression.spec.whatwg.org/#compressionstream)

共通APIのgzip対応範囲は単一メンバーとする。メンバーはgzip形式の独立した圧縮データ1個を指す。標準の`DecompressionStream`は、複数メンバーの連結や末尾の余分なデータをエラーとする仕様である。実装中の検証では、Node.js v24.15.0の`DecompressionStream`が連結gzipを受理した。この差を踏まえ、単一メンバーを対応範囲とし、連結gzipの拒否は環境依存として短く注記する方針を利用者と確認した。連結gzipの全環境での拒否は保証せず、専用の形式検証は追加しない。[Compression仕様のgzip定義](https://compression.spec.whatwg.org/#gzip)、[Node.js Gunzip](https://nodejs.org/api/zlib.html#class-zlibgunzip)、[Node.js v24.15.0の圧縮ストリーム実装](https://github.com/nodejs/node/blob/v24.15.0/lib/internal/webstreams/compression.js)

正常終了時は圧縮処理の終了と、展開処理の末尾検証まで確認する。tarの終端ブロックを読んだだけで成功扱いにせず、後から届くgzipのチェックサムエラーや入力エラーも呼び出し元へ伝える。

## 6. 読み取り、キャンセル、資源の解放

現在の展開処理は、前のファイルを読まずに次へ進む場合、その内容とパディングを読み飛ばす。内容は一度だけ取得できる。この基本動作を共通APIでも提供する。

ファイル内容のストリームを取得した場合は、読み切るか、そのストリームをキャンセルしてから次のエントリーへ進む。内容を読む処理と親のエントリー列挙が同じ入力を並行して読まないようにする。処理途中で親を進めようとした場合は、状態が分かるエラーにする。

ファイル内容だけをキャンセルした場合は、読み残した本文とパディングを処理して次のエントリーへ進めるようにする。アーカイブ全体のキャンセルや親の列挙終了では、元入力と圧縮処理を終了させる。途中まで読んだバイト数と残量を管理し、ファイル全体をもう一度読み飛ばさない。

現在の`iterator.return(value)`によるデータの差し戻しは、専用の読み取り処理へ分離する。標準イテレーターの`return()`は終了処理に使い、差し戻しと兼用しない。Web Streamsの非同期列挙の終了は、既定で入力のキャンセルにつながる。[Streams仕様](https://streams.spec.whatwg.org/#rs-asynciterator)

`AbortSignal`はループの前後で確認するだけでなく、読み取り待機中にも処理を終了できるようにする。終了・失敗・キャンセルのいずれでも、入力のキャンセル、readerのロック解放、圧縮処理の後始末を行う。任意の非同期ジェネレーター内の外部処理まで強制終了できるとは約束せず、入力側に必要なキャンセル対応も文書化する。

出力を読む側が停止した場合は、入力の読み取りも有限の先読みで止まる構成とする。文字列・バイト配列で全内容を取得するAPI、長さ省略時の全量収集、利用側が出力を`Blob`へ集約する操作は、逐次処理の経路と区別する。

## 7. 配布、開発環境、利用例

予定リリースバージョンは2.0.0とする。配布パッケージのバージョンは`screw-up`がGit履歴とタグから自動決定する。`package.json`の`version`は既存の仮値`0.0.1`を維持し、2.0.0のGitタグはリリース時に利用者が付ける。配布検証では固定値を前提にせず、Gitから算出したバージョンと成果物が一致することを確認する。

共通とNode.js専用のエントリーを、ESMの`.mjs`とCJSの`.cjs`で配布する。`package.json`の`exports`と型定義を対応させ、必要に応じてESM/CJSそれぞれの型定義を生成する。ブラウザ用の公開型から、`Buffer`や`node:stream`などの参照がたどれない状態にする。

共通成果物ではNode.jsモジュールの外部依存も残さない。Node.js専用成果物に必要な外部依存は残す。ビルド設定自体がNode.js上で動くことと、利用者へ配布するコードの依存を区別する。

TypeScript、Vite、Vitest、npmを継続して使う。`prettier-max`と`resolved-killer`を公式ドキュメントに従って設定し、既存の`screw-up`も依存指定と設定を確認する。外部ライブラリやWeb APIを使う際は、公式ドキュメントと型定義などのAPIコメントの両方を確認する。実装にはinterfaceとファクトリ関数を使い、公開APIへJSDocを記述する。

利用者向け文書の移行注記には「2.0.0で変更」と示し、旧APIからの変更点と新しい使い方を1〜2文程度で記す。対象は次のとおりとする。

| 説明箇所 | 短く注記する変更 |
| --- | --- |
| tarの生成とファイル内容の取得 | Node.jsの`Readable`からWeb Streamsへの変更 |
| バイト列での内容取得 | `getContent('buffer')`から`getContent('bytes')`へ、戻り値は`Buffer`から`Uint8Array`へ変更 |
| Node.jsのファイル操作 | import元を`tar-vern/node`へ変更し、ディレクトリーの属性取得もNode.js側へ分離 |
| gzip | 圧縮レベル9の固定を廃止し、単一メンバーを対応範囲とする。連結gzipの拒否は環境依存 |
| エラーとキャンセル | サイズ検証、入力の終了処理、展開先への逐次書き込みなど、利用者から見た動作の変更 |

対応環境の最低バージョンを変更する場合も、対象バージョンを短く併記する。注記は日本語の利用者向け文書を原本とし、英語READMEと配布用READMEの該当箇所にも反映する。

ブラウザでの観測用に、Viteで起動できる小さな利用例を用意する。ファイル選択からのtar作成、tarの選択と内容の列挙・読み取り、gzipの選択、キャンセルを操作できるようにする。大きな出力の逐次処理を検証する経路では、全出力を保持しない受け手へ流し、読み書きしたバイト数を表示する。ダウンロード用に全出力を`Blob`へ集約する場合は、その利用例だけが全体を保持することを区別して説明する。

## 8. 段階的な実装

各段階は動作を観測できる成果物とテストをそろえて完了させる。変更する動作のテストが失敗する状態をRED、実装後に成功する状態をGREENと呼ぶ。各段階でREDからGREENへの変化を確認する。新たな失敗が計画と食い違う場合は、実装を重ねる前に計画と原因を見直す。

各段階で対象テストとビルドを実行し、段階の完了時には既存の全体テストも確認する。コミットは段階内でも意味のある単位に分ける。公開機能を削除する場合は、削除を確認する一時テストでRED、削除後のGREEN、コミット、一時テストの削除というプロジェクトの手順に従う。使われなくなった実装は残さない。

実装用の作業ブランチは、対応issueがあれば`feature/<issue番号>`、なければ`feature/browser-support`とする。mainへのマージはこの計画の作業に含めない。

### 段階1. 通常のビルドとテストを再現できるようにする

成果物はnpmのコマンドで起動できる開発環境と、移植前の動作を確認できるNode.jsの実行例である。

1. lockfileと依存指定を確認し、`npm ci`後に通常のCLIが使える状態にする。
2. Node.jsとブラウザの検証対象を確定し、必要なWeb APIの利用条件を記録する。
3. フォーマットなどの開発設定を整え、既存コードの無関係な整形は分ける。
4. 既存のビルドと全テストを実行し、tar作成・展開を実行例から観測できる状態にする。

完了条件は、`npm run build`と`npm test`が通常の起動方法で成功すること、検証環境が再現できること、ビルドの警告を分析して対処していることである。

コミット例は`chore: prepare browser support verification`とする。

### 段階2. バイト処理とサイズの扱いを共通化する

成果物は`Uint8Array`でtarを生成・解析できる処理である。この段階ではNode.jsのストリームへ接続して実行可能な状態を保つ。

1. 通常の`Uint8Array`、UTF-8、空ファイル、不正な長さ、サイズ過不足のテストでREDを確認する。
2. バイト列の確保、コピー、連結、文字列変換を共通処理へ移す。
3. `length: 0`と未指定を区別し、宣言サイズと実サイズの一致を検証する。
4. 長さ省略時の全量収集をNode.jsの`Readable.from()`へ依存しない形にする。

完了条件は、文字列・バイナリー・空ファイルの往復が成功すること、サイズ不一致が明示的に失敗すること、Node.jsの既存用途と外部tarとの相互運用が動作することである。

コミット例は`refactor: use portable byte operations for tar entries`とする。

### 段階3. ストリーム処理と公開エントリーを分離する

成果物は共通エントリーからブラウザ向けにビルドできる非圧縮tarと、Node.js専用エントリーから使えるファイル操作である。

1. Web Streamsによる非圧縮tarの生成・展開、分割チャンク、キャンセルのテストでREDを確認する。
2. 内部の非同期反復処理とWeb Streamsの接続を実装する。
3. データの差し戻し、内容の単回取得、未読内容の読み飛ばし、部分読出しを整理する。
4. 共通ヘルパー、公開型、Node.jsのファイル操作を別モジュールへ分ける。
5. `tar-vern`と`tar-vern/node`のビルドと型定義を用意する。
6. Node.jsの実行例とテストを新APIへ移す。gzipの既存動作は、共通対応が完了するまでNode.js側で実行可能に保つ。

完了条件は、非圧縮の共通成果物をNode.js依存なしでブラウザ向けにビルドできること、読み取りとキャンセルのテストが成功すること、Node.jsのファイル操作を実行できることである。

コミット例は`refactor: separate portable tar streams from node helpers`とする。

### 段階4. File・Blob入力とブラウザの利用例を追加する

成果物はファイル選択から非圧縮tarを生成・展開できるブラウザの利用例である。

1. 既知サイズの入力が全体を先読みしないこと、出力側が止まると入力も有限の先読みで止まることをテストする。
2. `File.size`または`Blob.size`と`stream()`を使う補助APIを実装する。
3. 利用例からファイル選択、内容の読み取り、キャンセルを操作できるようにする。
4. Playwright MCPで実ブラウザを操作し、公開成果物を使った処理を確認する。

完了条件は、日本語名・空ファイル・バイナリーを含む選択ファイルを処理できること、内容を全体保持せずに受け取る経路で逐次動作を確認できること、アーカイブ全体のキャンセル後に入力の読み取りが継続しないことである。

コミット例は`feat: stream selected browser files into tar archives`とする。

### 段階5. 共通のgzipとエラー処理を完成させる

成果物はブラウザとNode.jsの両方で利用できるtar.gzの生成・展開である。

1. gzipの往復、外部tarとの相互運用、破損データ、入力エラー、キャンセルをテストする。
2. 標準の圧縮・展開ストリームを共通処理へ接続する。
3. 入力から出力までのエラー伝達と終了処理を確認する。
4. gzipの末尾検証、単一メンバーの扱い、APIが使えない場合のエラーを確定する。
5. 移行のために残したNode.js側の重複処理を整理し、利用例へgzipを追加する。

完了条件は、両環境で作成したtar.gzを相互に展開できること、gzip末尾の破損を成功扱いにしないこと、アーカイブ全体のキャンセルとエラーで処理が停止し未処理の例外が残らないことである。

コミット例は`feat: support portable gzip streams and cancellation`とする。

### 段階6. 配布成果物、CI、利用者向け文書を確認する

成果物はブラウザとNode.jsの両方から利用できる配布パッケージと、その使い方を説明する文書である。

1. Gitから算出したバージョンで生成した配布パッケージを利用側プロジェクトへ導入し、バージョン、ESM、CJS、ブラウザ向けビルド、型チェックを確認する。
2. 共通処理とNode.js連携の自動テストをCIへ組み込む。ブラウザ検証の対象と再現手順も固定する。
3. 日本語の利用者向け文書を`docs/ja/README.md`に作り、その内容を原本として既存の英語READMEと配布用READMEを更新する。
4. サイズが既知の入力、長さ省略時の全量収集、エントリーの消費順序、キャンセル、gzipの範囲、Node.js専用APIを説明する。変更したAPIや動作の説明箇所に、7章の方針に沿った短い移行注記を添える。
5. 全体テストと対象ブラウザの検証を実行し、次節の完了条件を確認する。

一般の利用者向け文書から本計画書へのリンクは追加しない。利用者向け文書では公開APIと利用条件を説明し、内部実装の手順をなぞる説明は本計画書にとどめる。

完了条件は、Gitから算出したバージョンの配布成果物だけで利用例と型チェックが成立すること、対象環境の検証が成功すること、利用者向け文書と移行注記が実装の動作と一致することである。

コミット例は`chore: verify browser and node package distribution`と`doc: describe browser and node usage`とする。

## 9. 検証内容と全体の完了条件

| 検証対象 | 確認する動作 |
| --- | --- |
| tar形式 | ヘッダー、チェックサム、512バイト境界、終端、空ファイル、ディレクトリー、メタデータ |
| 文字列とバイト列 | 日本語・絵文字の名前、UTF-8の境界、本文のBOM、バイナリー、長いパスの現行動作 |
| チャンク | 1バイト単位を含む分割、ヘッダー・本文・パディングをまたぐ入力、複数エントリーを含む入力 |
| サイズ | 正常な長さ、0バイト、不正な長さ、過不足、長さ省略時の収集、File・Blobからのサイズ受け渡し |
| 内容の取得 | 文字列、バイト列、ストリーム、未読スキップ、二重取得の拒否、部分読出し後のキャンセル |
| 逐次処理 | 本文を全部読む前の出力開始、有限の先読み、出力消費に応じた入力の進行 |
| 終了と失敗 | 事前中断、読み取り待機中の中断、親列挙の終了、入力エラー、圧縮エラー、readerの解放 |
| gzip | 両環境での往復、外部tarとの相互運用、途中切断、末尾の破損、連結メンバーと余分なデータの扱い |
| 配布と型 | ESM/CJSからの利用、ブラウザ向けimport、Node.js型定義なしの型チェック |
| 実ブラウザ | Playwright MCPによるファイル選択、公開成果物の利用、生成・展開、キャンセル |

逐次処理のテストでは任意の時間だけ待って成功を推測しない。入力チャンクの供給と出力の消費をテスト側で制御し、読み取り回数や完了の通知で確認する。有限の先読みは許容し、入力を一切先読みしないという過剰な条件にはしない。

移植後のコード同士による往復だけで正しさを判定せず、外部tarで生成したデータの展開と、tar-vernの出力を外部tarで展開する検証も残す。テストではアセットの配置や実装手順ではなく、内容と利用者から見た動作を確認する。

ブラウザ検証をNode.js上のWeb APIテストで代用しない。必要なPlaywright MCPやブラウザが使えない場合は、検証環境を用意してから完了を判断する。

全体の完了条件は次のとおりとする。

- [x] 共通成果物と公開型がNode.jsのモジュール、`Buffer`、Node.jsの型定義を必要としない。
- [x] ファイル選択からの入力はサイズを渡し、本文全体の先読みなしでtarへ供給できる。
- [x] 既知サイズの入力とストリーム出力の経路で、入力全体を保持せずバックプレッシャーが働く。
- [x] 非圧縮tarとgzipの生成・展開が、対象ブラウザとNode.jsで動作する。
- [x] 空ファイル、サイズ不一致、部分読出し、キャンセル、破損入力を定義した動作で処理する。
- [x] Node.js専用APIからファイル操作とディレクトリー走査を実行できる。
- [x] ESM/CJSとブラウザ向けの利用側プロジェクトが配布パッケージのみで動作し、型チェックが成功する。
- [x] 全体テスト、外部tarとの相互運用、実ブラウザ検証が成功し、ビルドの警告を処理済みである。
- [x] 日本語を原本とする利用者向け文書に、対応環境とサイズ・メモリ・gzipの制約を記載している。
- [x] 配布パッケージのバージョンがGitから算出した値と一致し、利用者向け文書の変更箇所に短い移行注記を記載している。
- [x] 使われなくなった実装と移行用の一時テストを整理し、段階ごとのコミットを作成している。

## 10. 実施結果

作業ブランチは`feature/browser-support`。mainへのマージとnpmへの公開は行っていない。Gitから算出したバージョンで配布パッケージを`artifacts/`へ生成し、独立した利用側プロジェクトへインストールして検証した。

| 段階 | 成果と確認 |
| --- | --- |
| 1 | npm ciでCLIを復旧。既存57テストとNode.jsの利用例が成功。整形・型検査、resolved-killer、screw-upを設定 |
| 2 | Uint8Arrayへ移行。既知の0バイト、不正な長さ、実サイズの過不足をREDからGREENへ変更。全69テストが成功 |
| 3 | 共通APIとNode.js専用APIを分離。読出し待ち、親の終了、部分読出し、保存先エラーでのキャンセルを確認。ブラウザ用バンドルの生成と全91テストが成功。旧API削除の一時テストは確認・コミット後に除去 |
| 4 | File・Blobヘルパーとブラウザ例を追加。全92テストと3エンジンの実操作が成功 |
| 5 | 標準gzipへ移行。全101テスト、3エンジンでの往復・CRC破損・中断、Node.jsとの相互運用が成功。移行用のNode.js gzip接続は削除 |
| 6 | Gitから算出したバージョンでの配布確認、CI、利用者向け文書と短い移行注記を整備。事前中断と親return中断の追加検証を含む最終103テストが、Node.js 22.17.0と24.15.0で成功 |

実装中に確認した計画との差は、Node.js標準APIが連結gzipを受理する点である。利用者の確認を経て、単一メンバーを対応範囲とし、連結gzipの拒否は環境依存として注記する方針へ更新した。保存先の書き込みエラー時は、Node.jsのpipelineが渡すsignalを入力へ伝播し、読み取り待ちを終了する。

再現用の検証コマンドは次のとおり。

`npm ci`、`npm test`、`npm run typecheck`、`npm run typecheck:browser`、`npm run build:example`、`npm run test:package`、`npm run test:browser`。

実ブラウザ検証には`npx playwright install --with-deps chromium firefox webkit`で用意したブラウザを使う。検証スクリプトはPlaywright MCP経由でファイル選択とUI操作を行い、時間経過による推測を避けて完了通知と入力の制御で判定する。`test-results/browser/`の通常tar・gzip画面も3エンジンとも目視確認した。

配布検証ではESM/CJS双方の生成・展開・ファイル保存、Node.js型定義を読み込まない型チェック、ブラウザ向けバンドルを確認した。ビルドの警告はなく、npmによるesbuildのインストールスクリプト確認も設定済みである。
